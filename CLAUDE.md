# Dome Keeper: Story Mode mod

This folder is the decompiled Dome Keeper project (Godot 4.3.1, custom build). We are building a Story Mode mod: a Motherload-style descent with a money economy, a depth-based mineral ladder, story text boxes from a monster in the depths, and metal gates that only the Suit Blaster can break.

- Design goals: https://claude.ai/artifact/2uRKfLccTeaYAzEsKDNzrA
- Build plan and issue board: GitHub Issues on https://github.com/cejdan/Dome-Keeper-Story-Mode-Mod. The wayfinder map is issue #1 ("Story Mode mod"); its tickets are sub-issues.
- The mod: `mods-unpacked/cejdan-StoryMode/` (`manifest.json`, `mod_main.gd`)
- Modding wiki: https://github.com/DomeKeeperMods/Docs/wiki
- Engine: `../custom_godot_for_windows/godot.windows.editor.x86_64.exe`
- Art: LibreSprite in `../tools/libresprite`, driven by scripts; pipeline and the game's palette encoding in `art/README.md`
- Vanilla game code is reference only. Mod code goes in `mods-unpacked/<Author-ModName>/`, never edits to vanilla files.

## Working rules

- The user is mostly away. Verify every change by playtesting it in the running game (playtest harness, screenshots, frame bursts, state logs) before calling it done. Report what was seen, not what was expected.
- Game-design calls (values, feel, story, scope) are the user's: leave them as HITL tickets. Technical how-to calls are yours: resolve them by spike and record the reasoning on the ticket.
- One ticket per session, except research tickets.
- Script extensions go in `extensions/installer.gd` (#252, #256). Once one takes over a vanilla `class_name` script's path, a script compiled after that can't use the class in a type: `extends Map` fails to compile, `var d: Dome` goes untyped ("Compiler bug: unresolved assign"), `x is CaveBomb` is true for anything. So every script that names an extended class in a type is compiled and held before the install (`NAMED_BY`), a vanilla `class_name` subclass that needs the extension's behaviour gets its own extension (dome3.gd), and the install order follows the comment there. After adding an extension or a script that names one of those classes, run `t252_class_names`: it rescans the project and says what is missing.
- Story Mode is its own game mode; vanilla modes must keep working. Since 2026-11-16 it must also work in v5 multiplayer (online co-op and splitscreen; map #222): host-authoritative, `Data.apply` only on the host, anything a client's keeper does to the team goes to the host.

## Version control

- This folder is a clone of https://github.com/cejdan/Dome-Keeper-Story-Mode-Mod (branch `main`). `.gitignore` ignores everything by default and allowlists only our files (`mods-unpacked/`, `docs/`, `art/`, `CLAUDE.md`, `GLOSSARY.md`, `README.md`, `override.cfg`). Never commit vanilla game files; to track a new top-level file of ours, add a `!/<name>` line to `.gitignore`.
- Never work on `main`. Each ticket gets its own branch off an up-to-date `main`, named `ticket/<issue>-<short-slug>` (e.g. `ticket/6-mod-skeleton`). Push the branch and open a PR into `main` that links the issue. Merge only when the user says so.
- One commit per ticket, made when the ticket resolves, covering its code and assets. Message: `#<issue>: <ticket title>`, then a line or two on what changed and how it was verified.
- Before committing, run `git status` and check that only our files are staged.
- To roll back a ticket's change, `git revert` its commit. Don't rewrite history or force anything.

## Running the game

- Launch: `../custom_godot_for_windows/godot.windows.editor.x86_64.exe --path "<abs path>/Dome Keeper"`. The project is in dev mode and skips the title screen.
- **Real saves are off limits.** `override.cfg` gives dev runs their own user folder, `%APPDATA%\StoryModeDev`, with logs in `logs/godot.log` and `logs/modloader.log`. Without it, runs write into the real Steam save folder (`%APPDATA%\Godot\app_userdata\Dome Keeper`) and rotate the player's saves out. Never remove `override.cfg`, and never write to the real folder.
- **Dev runs don't report to the developers' Sentry.** `project.godot` holds Bippinbits' Sentry DSN, and the SDK starts and sends even with `allowCrashReports: false` in the dev `options.txt`. `override.cfg` sets `[sentry] options/enabled=false`, so godot.log shows `Sentry SDK is disabled in the project settings.` and no `envelope` requests. Keep that key in `override.cfg`; if a run's godot.log shows `starting Sentry SDK`, stop and fix it before launching again.
- Mod loaded? `modloader.log` should show `cejdan-StoryMode: Init` and `Done`. The title-screen Modding button is hidden in this game version.

## Playtest harness

Dev-only code in `mods-unpacked/cejdan-StoryMode/dev/` (left out of release builds). It runs one scenario in the real game and exits.

- **Run:** `& "<...>\Dome Keeper\mods-unpacked\cejdan-StoryMode\dev\playtest.ps1" <scenario> [-Timeout 300] [-Res 1280x720] [-Extra "--foo=1"]` from PowerShell. It refuses to launch without `override.cfg`, kills a hung run after the timeout (300 s, or the scenario's own `const TIMEOUT := <seconds>`, unless `-Timeout` is given), and prints the exit code (0 = every check passed), the error lines found in the log, each PASS/FAIL line and a `VERDICT: PASS|FAIL` (its own exit code says the same). The error scan (`dev/log_scan.ps1`, #249; `mp_playtest.ps1` runs it on every instance) counts script errors anywhere and `USER ERROR` lines between scenario begin and end, minus a short commented allowlist of vanilla and engine noise; any other error line fails the run. Add to the allowlist only what is shown to be vanilla or engine, with where it comes from.
- **Output:** `..\playtest_out\<scenario>\` (outside the repo): numbered screenshots (`NNN_<label>.png`), frame bursts (`NNN_<label>_fNN.png`), map overviews, `log.json` (events, state snapshots, checks) and `godot.log`. Look at the screenshots before calling something done.
- **Write a scenario:** add `dev/scenarios/<name>.gd` extending `dev/scenario.gd`. `boot()` returns what to start: `mode` (default `storymode`; `relichunt` for vanilla checks), `seed`, `gadget`, `difficulty`, `world`, `palette`, `loadout: true` for the loadout screen, or `load: <slot>` to load a save (`singleplayer` folder) the way Continue does, for save/reload checks across a real relaunch (save first with `SaveGame.saveGame("singleplayer", <slot>, true)` in an earlier scenario; see `t23_beat_box` / `t23_beat_reload`). Story beats pause the game, so the harness marks every beat played before `run()` unless `boot()` returns `beats: true`. The keeper's welcome log, which opens every new run, stays muted even then unless `boot()` also returns `welcome: true` (see `t123_keeper_log`). `run(h)` is a coroutine that drives the game through the harness `h` (`dev/harness.gd`):
  - input: `await h.hold("ui_down", 3.0)`, `await h.press("ui_select")`, `h.down(action)` / `h.up(action)` (real key events built from `InputMap`; an action bound only to a mouse button sends that button), `h.aim_mouse(world_pos, k)` (keeper3 aims its kunai and rope at the mouse on the keyboard)
  - time: `await h.wait(sec)`, `await h.frames(n)`, `h.speed(scale)`, `await h.until(callable, timeout)`
  - capture: `await h.shot(label)`, `await h.burst(label, frames, every)`, `h.snap(label, extra_data_keys)`, `h.map_png(label, colors)` (whole-map picture from tile data), `h.note(label, data)`
  - checks: `h.check(label, ok, data)`; any failed check makes the run exit 1
  - story: `await h.read_beat(label)` waits for a story beat, shoots each page and closes it (returns its id); `h.beat_box()` is the open box
  - setup: `h.disable_waves()`, `await h.reveal_all()`, `await h.dig_room(a, b)`, `await h.teleport_tile(coord)`, `h.set_inv(type, n)`, `await h.deliver(type, n)`, `await h.buy(upgrade_id)`, or any direct `Data` / `Level` / `GameWorld` call
- **Dev boot without a scenario:** `-- --story` boots straight into a Story Mode run, `-- --mode=relichunt` a vanilla run, `-- --loadout` the loadout screen; `--seed=`, `--gadget=`, `--difficulty=`, `--load=<slot>` as above (`dev/dev_boot.gd`); `-- --story --horror-defeated` plays the saved ending; `-- --story --boss` drops the keeper into Velle's chamber for the boss fight (`--boss=chase` starts at the chase, `--boss=finale` at the surface battle; the first two drill a winding shaft from the chamber up to the dome, the way home in the chase). All three start with the gear of a keeper who got that far, for every keeper: max drill and jetpack, Laser IV, a stronger dome, Heat Shielding IV and the Suit Blaster (`dev/boss_dev.gd`).
- **Finding hazards by hand:** add `--gas` to a `-- --story` launch and F10 puts the keeper in a tunnel beside the next gas pocket (drill into the green cracks); `--lava` and F9 do the same for magma pockets.
- **Online multiplayer playtests (#223):** `& "<...>\dev\mp_playtest.ps1" <host scenario> <client scenario>` runs two instances on this machine over ENet (127.0.0.1): the host boots with `nethost: true` (hosts, then opens the loadout; its scenario starts the run with `stage.gameModeSelected("storymode")` and `stage.startRun()` once the client is in, then calls `h.mute_beats()`; `host_start(h, players, mode, dome, keepers)` picks each player's keeper, the Engineer for all by default in Story Mode, as `t231_split_restart.start_split(h, keepers)` does in splitscreen; every keeper is playable in Story Mode since #297, `t297_*`), the client with `netjoin: true` (joins and follows the host's stages; its scenario starts once its run is playable). By hand: `-- --nethost` and `-- --netjoin`. `Keepers.first()` is the instance's own keeper (it errors while there is none; mod code calls `Story.local_keeper()`, which returns null then); `Data.apply` only works on the host. See `t223_mp_host` / `t223_mp_client`. A Data change can overtake a big (chunked) Data message to a client and be undone by it there; `net/story_net.gd` resends what went stale once those messages have landed (#242; `t242_mp_data_resend_*`, `-Extra "--noresend"` shows the race without it). Since #246 a Data message to a peer that already has one queued in the chunker waits behind it instead of overtaking it (`net/ordered_chunker.gd`; `t246_mp_late_join_*`, `-Extra "--vanillachunker"` turns it off); since #261 only the keys a queued message holds wait, the rest of a delta goes at once (a big one too, in pieces under the chunk size, #268), so a new gadget's keys still beat the RPC that adds it; keys sent ahead of a full sync still on its way go back in once it has landed on the client (#268). `t253_mp_blaster_* -Extra "--give=drill --onedelta"`, `--fullsync`, `--bigdelta`; `--heldchunker` shows the old order. Data stays small (#247): the map facts go to clients as StoryNet RPCs, not a Data key, and the chunker takes the lava and gas save blobs out of every big Data message. `-Extra "--datasizes"` logs, from the host, every chunked Data message key by key (and each full sync's biggest keys' share of its compressed size) and a tally of all Data messages every 20 s; the one-line summary of each chunked Data message is always logged.
  - Saves and late joins (#232): `-- --netload=<slot>` (boot key `netload`) loads an online save from the `multiplayer` folder the way Continue Multiplayer does: it hosts and opens vanilla's keeper choice, where the host scenario picks the saved keepers and starts (`t232_mp_load_host`; give the client `-ClientDelay 12`). In `t251_mp_load_*` each player walks into its own saved keeper (`h.walk_into_choice()`); `t251_mp_save_*` / `t251_mp_load_*` with `-Extra "--vanilla"` do the same in Relic Hunt, and `--instantpick` has the host take its keeper the moment the client joins (the #251 race, avoided in Story Mode by `extensions/stages/deviceselection/DeviceselectionStage.gd`). Save one first with `SaveGame.saveGame("multiplayer", <slot>, true)` on the host (`t232_mp_save_host`). A player can join a run under way only as the keeper of a player who left: `-Rejoin <scenario>` starts that client once the last client has quit, and the harness takes the free keeper for it in the keeper choice (`t232_mp_dropin_*`). `-Client2 <scenario>` adds a second client, a third instance (`t246_mp_late_join_*`). `mp_scenario.gd` has `setup_run_state()` / `facts()` / `check_facts()` for comparing a run's Story Mode state across instances.
- **Local splitscreen (#231):** boot `{"loadout": true, "splitscreen": true}` (by hand `-- --loadout --splitscreen`) opens the loadout the way the title's Splitscreen button does; `await h.join_device(0)` (keyboard) and `h.join_device(1)` (gamepad 1) join, then the scenario picks Story Mode and starts (`t231_split_restart.start_split(h)` does all of it). Drive keeper 2 with `h.pad_stick(1, dir, sec)` (gamepad keepers walk with the stick), `h.pad_press(1, action)`, `h.pad(1, action, pressed)`; `h.teleport_tile(c, k)` / `h.snap_camera(k)` take a keeper; `h.local_keepers()`. `h.shot()` captures both split views at once. With `nethost` too, the host plays two local keepers online (`t231_mp_split_*`). Boot `title: true` starts at the title screen (`t231_title_again` presses its buttons). Mod code loops over `Story.local_keepers()` for anything per keeper (heat, toxin, recall, bars, heat lines); Heat Shielding and the Suit Blaster entry are per-player keeper-tree upgrades like vanilla's drill (`player2.storyheatshield1`, Data `player2.suit.heatshield`, limit `<playerId>.storykeeper`; `gamemode/keeper_upgrades.gd`, #265), and `h.buy(id, k)` buys as keeper `k`; `Story.view_rects()` are the split views' world rects (culling must cover all of them, `t231_split_lava`); something screen-space for one keeper goes in that keeper's view with `Level.viewports.showForLocalKeeper(k, item)` on a world item (a CanvasLayer with `custom_viewport` errors when the level is freed); screen text goes on a world node kept on that keeper's camera and scaled by 1/zoom (the pleas, `t263_split_pleas`; the chase's edge marks, `t263_split_chase`).
- Scenarios are named `tNN_<what>.gd` after the ticket they verify; keep them, they are the regression suite.
